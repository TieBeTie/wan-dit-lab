# Проверка prefetch блоков

Измеряем, успевают ли веса следующего блока попасть в VRAM до его вычисления. Проверка относится к отдельному C++ DiT runner, не к полному конвейеру T5 → Self-Forcing → VAE.

## Протокол

- Пространственное разрешение 480×832, латентная сетка 9×30×52, 30 блоков.
- Окно 1, 2, 3 или 4 слота. Один слот занят текущим блоком; остальные позволяют готовить следующие.
- В каждом варианте два запуска по 7 проходов. Для времени берём проходы 2–5, исключая прогрев и финальную очистку.
- Существующий нативный manifest хранит передаваемые веса в FP32; вычисления скомпилированы с BF16. Это отличается от BF16 offloading полного Python-конвейера.
- Снимки памяти внутри блоков отключены, чтобы не мешать перекрытию копирования и вычислений. Пиковая память измеряется CUDA allocator за весь запуск.
- Дополнительно искусственно задерживаем каждую передачу или подготовку весов на 200 мс. Проверяем ожидание готовности и правильность выхода.

## Было → стало

| Часть | Было | Стало | Измеренный эффект |
| --- | --- | --- | --- |
| Буферы весов | 2 pinned RAM / 2 VRAM, задано вручную | Параметризованное окно; расчёт по идее FlexGen оставил 2 / 2 | К прежнему 2 / 2 ускорение не измерено; выбранное расписание то же |
| Выбор окна | Без расчёта стоимости | Измеряем подготовку, перенос, вычисление; моделируем окна 1–4 | Модель выделила 2 / 2 как минимальное достаточное окно |
| Контроль 1 → 2 слота | 4,098 с | 3,669 с | Сокращение времени 10,5%; это эффект перекрытия, не добавления FlexGen |
| Время жизни ресурсов, отдельный замер | 0,587 GiB allocated VRAM после работы | 0,009 GiB после работы | Освобождение ресурсов; не оценка ускорения prefetch |

Реализована собственная упрощённая модель стоимости по идее [FlexGen, §4.2–4.3](https://arxiv.org/html/2303.06865). Полный оптимизатор размещения FlexGen не подключён. Расчёт выполняется в эксперименте; runner получает окно явно через `--window`. Сравнение времени до и после добавления расчёта на неизменном окне 2 / 2 не проводилось.

## Расчёт расписания

Для каждого блока измеряем:

$$
\underbrace{P_i}_{\text{RAM → pinned RAM}},\qquad
\underbrace{H_i}_{\text{pinned RAM → VRAM}},\qquad
\underbrace{C_i}_{\text{вычисление блока}}.
$$

Модель симулирует последовательные очереди подготовки, копирования и вычисления. Копирование ждёт окончания использования прежних весов в том же слоте; вычисление ждёт завершения копирования. Основа расчёта:

$$
\mathrm{start}_i^{\rm compute}
=\max\bigl(\mathrm{finish}_i^{\rm copy},\mathrm{finish}_{i-1}^{\rm compute}\bigr).
$$

Измеренные стоимости подставляем в модель и сравниваем окна. Выбираем наименьшее окно, которое устраняет существенное ожидание и помещается в память. В runner окно задаётся через `--window`; автоматический выбор для полного конвейера пока не подключён.

CUDA event интервалы включают задержки подачи работы из CPU. Это не измерение чистого времени активности GPU-ядер. `gpu_ready_gap_ms` измеряет интервал перед вычислением блока, `gpu_dependency_wait_ms` отдельно охватывает ожидание события загрузки после постановки копирования в очередь. Полное время прохода включает также входные и выходные операции; модель оценивает только цепочку блоков.

## Результаты: 2026-10-18

| Слоты | Время прохода, с | Интервал готовности p50 / p99, мс | Пик allocated VRAM, GiB | Модель цепочки, с |
| --- | ---: | ---: | ---: | ---: |
| 1 | 4.098 | 15.0401 / 15.4699 | 1.137 | 4.237 |
| 2 | 3.669 | 0.0031 / 0.0256 | 1.310 | 3.704 |
| 3 | 3.679 | 0.0031 / 0.0221 | 1.483 | 3.704 |
| 4 | 3.681 | 0.0031 / 0.0248 | 1.656 | 3.704 |

В этой конфигурации оставляем два слота: текущий блок и следующий. Время на 10,5% меньше, чем при одном слоте, дополнительные слоты увеличивают память без заметного ускорения. Это два повтора на одной машине, не оценка статистической значимости универсального выигрыша.

Расчёт верно выделяет два слота как минимальное достаточное окно. Абсолютные времена грубые: подставляем медианы этапов из перекрывающегося исполнения, CPU-подача работы и конкуренция ресурсов меняются при смене окна. Отдельная цепочка в модели может даже оказаться длиннее измеренного полного прохода. Это расчёт для сравнения вариантов, не точный предиктор времени.

| Искусственная задержка на каждом блоке | Проход, с | Интервал готовности p50 / p99, мс |
| --- | ---: | ---: |
| Перед копированием: +200 мс | 6.991 | 22.25 / 36.89 |
| Подготовка в RAM: +200 мс | 6.554 | 29.31 / 39.12 |

При задержках вычисление ждёт готовности весов. Все 30 сохранённых выходов из 10 случаев побитно одинаковы. Относительная L2-ошибка относительно eager-эталона 0,007842, максимальная абсолютная 0,023438, в установленных пределах 0,01 и 0,25. Здесь проверены первый, второй и последний выход каждого запуска, не каждый промежуточный проход.

Проверки: 2 CPU-теста модели расписания; сборка нативного runner; 10 GPU-случаев; Ruff.

## Воспроизведение

Из корня проекта:

```powershell
.venv/Scripts/python.exe -m pytest tests/test_prefetch_model.py -q
.venv/Scripts/python.exe benchmarks/bench_prefetch.py
```

Нужны существующие AOT-пакеты в `artifacts/wan_aot`. Протокол, сырые события, ошибки выхода и результаты сохраняются в `artifacts/prefetch_check`. Повторный запуск использует завершённые случаи с тем же протоколом и хешем исполняемого файла.
