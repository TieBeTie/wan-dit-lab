# RoPE 3D: локальная разработка через тесты

Изолированное ядро: `src/wan_dit_lab/kernels/rope_triton.py`. Исходный `rope.py` и вызовы
в модели сохранены. Новая реализация доступна явно, но не включена по умолчанию.
Для разработки и проверки не нужны checkpoint, T5, VAE или генерация видео.

## Одна точка входа

Из PowerShell в корне проекта:

```powershell
.\scripts\check_rope.ps1
```

`-OpenReport` открывает готовый HTML-отчёт в новой вкладке браузера.
В отчёте две сопоставимые колонки, PyTorch и Triton. Основной случай выбирается
через `summary_case` в конфиге. Остальные размеры раскрываются отдельно.

Реальный live, последовательно PyTorch и Triton:

```powershell
.\scripts\check_rope.ps1 -Live -OpenReport
```

Используется Windows-окружение рабочего Live, с его W4A4 и SageAttention.
Перед новым сравнением текущее окно Live должно быть закрыто. Настройки сравнения
задаются в `configs/experiments/rope_live.json`: тот же teacup-промпт и seed,
512×928, 2 шага, 24 streamed-блока, 6 прогревочных и 24 измеряемых чанка.
Таблицы частот в этом preset FP32, и ядро сохраняет FP32-арифметику. Базовый
FP64-эксперимент остаётся отдельным измерением. Обе live-ветки используют одинаковую
компиляцию фиксированных размеров. Смена промпта делает замер недействительным.

FPS генерации считается по фактически декодированным кадрам и сумме времени
DiT + TAEHV + перенос/преобразование пикселей, без блокировки очередью окна.
FPS показа считается отдельно по фактическим извлечениям кадров из очереди во
время измеряемого интервала. Это не измерение частоты обновления монитора.
Окно ограничено 24 FPS. После сравнения Triton Live остаётся открытым до Esc.
Исходный `live_video.py` не редактируется: выбор RoPE и точки измерения действуют
только в процессе обёртки. Размер и mtime checkpoint проверены при исправлении
единственного устаревшего пути в манифесте W4A4 после переноса проекта.

Обёртка запускает единственный Python runner в существующем WSL-окружении.
Внутри WSL можно запустить тот же runner непосредственно:

```bash
/home/rama/.venvs/wan-rope/bin/python scripts/checks/check_rope.py
```

Только базовые проверки: `check_rope.ps1 -TestsOnly` или
`python scripts/checks/check_rope.py --tests-only`. Полный запуск всегда сначала выполняет
тесты. Пропущенные CUDA-тесты не считаются успешной GPU-проверкой.

Настройки: `configs/experiments/rope_triton.json`. Каждый запуск создаёт новый
каталог с `tests.log`, `results.json`, `Report.md` и `Report.html` во внешнем каталоге экспериментов.
`latest.json` в родительском каталоге указывает на последний завершённый прогон,
включая неудачный, чтобы предыдущий успешный результат не скрывал ошибку.
Ошибки и неудачные измерения сохраняются. Код возврата ненулевой при ошибке
корректности, неправильном числе ядер, перекомпиляции при измерении или регрессии.

## Контракт и разработка

1. Сначала написаны тесты, зафиксирован `tdd_red.log`: модуль ещё отсутствовал.
2. Написано отдельное ядро, тестами найдены расхождения округления.
3. Исправлено приведение FP64 в FP16/BF16 внутри регистров, без глобального буфера.
4. Добавлены тесты регистрации оператора, первого и второго градиента,
   `torch.compile(fullgraph=True)`, autocast, другого CUDA stream и целого блока.
5. Только после корректности запускаются парные измерения через общий harness.

Вход: `(batch, token, heads, dim)`. Частоты: `(cos/sin, position, pair)`.
Разбиение пар по осям совпадает с исходником: временная ось получает остаток
после двух равных пространственных частей. Временной сдвиг задаётся `start_frame`.
Пары обрабатываются независимо. Поворот вычисляется в FP64 и сразу записывается
в итоговый тензор. Временных FP64-тензоров размера входа нет.

Поддерживаются FP16/BF16/FP32/FP64, разные сетки внутри batch, padding,
непрерывные и strided-входы, strided-градиенты и CPU-метаданные сеток.
Для полного графа передаются Python-сетки. CUDA-тензор размеров отклоняется,
чтобы не скрывать синхронную передачу метаданных на CPU.
Частоты считаются константами, градиенты по частотам не поддерживаются.
Адаптер `rope_apply_wan` принимает комплексные частоты upstream Wan и возвращает FP32.

## Метрики на каждом полном запуске

| Проверка | Что показывает |
|---|---|
| Finite, форма, dtype, padding, неизменность входа | Соблюдение контракта |
| Максимальная абсолютная ошибка, RMSE, относительная L2-ошибка, число несовпадений | Исходник и новая версия, eager и compiled |
| Ошибка против вещественного FP64-эталона для обеих версий | Изменение численной точности после округления выхода |
| Ошибка всего compiled-блока против независимого FP32-блока | Интеграция с учётом fusion и низкой точности |
| Сохранение нормы, общий сдвиг позиций, цельный ролик против чанков | Структурные свойства вращения и индексация трёх осей |
| Градиенты, gradcheck, gradgradcheck, opcheck | Производная и регистрация в PyTorch, проверяются отдельно |
| p50/p90/p95/p99, min/mean/max, сырые парные измерения | Распределение GPU-времени |
| Отдельное wall time обычного compiled-вызова | Python-подача работы и ожидание завершения GPU, без CUDA graph replay |
| Отношение времени, bootstrap-интервал, порог регрессии | Контроль скорости на том же GPU и входах |
| Allocated/reserved до операции и их пики, дополнительный peak allocated, свободная VRAM до/после | Разделение живых тензоров, кеша аллокатора и памяти устройства |
| RSS high-water mark процесса | Пиковая RAM всего runner, не отдельного оператора |
| Число и имена GPU-ядер | Проверка, что forward RoPE действительно выполняется одним ядром |
| Первый вызов, число графов, отсутствие перекомпиляции при замерах | Отделение компиляции от steady state |
| Tokens/s и полезные input+output GB/s | Производительность для данного размера, не измеренный DRAM-трафик |
| Версии, GPU, commit, SHA256 исходников, seed, конфиг | Воспроизводимость |

PSNR, SSIM, размытость и другие видеометрики здесь не применяются: меняется
реализация одного оператора с известным эталоном. Полная генерация и качество
видео являются отдельным экспериментом, их ускорение по этим данным не заявляется.

## Что следует из статей

| Источник | Что обосновывает для нашего эксперимента |
|---|---|
| RoFormer, разделы 3.2–3.3, формула (16), с. 4–6 | Проверки вращения, сохранения нормы и зависимости attention от относительной позиции |
| FlashAttention, разделы 3.2 и 4 | Отдельно измерять обращения к памяти, её пиковый объём, время оператора и время всей модели |
| Triton, MAPL 2019, раздел 6 | Сравнение с базовой реализацией на разных размерах, оценка вычислительной производительности |
| NVIDIA Nsight Compute, Roofline и Memory Workload Analysis | Профиль трафика, вычислительных ограничений и аппаратных причин задержек |

Ни одна из этих работ не задаёт универсальный обязательный список p50/p90/p99
для RoPE. Наша программа проверок является инженерным выбором под замену оператора.

Основной результат: ошибка выхода и производной, структурные свойства RoPE,
GPU-время и wall time, дополнительный peak VRAM, число ядер, ускорение целого блока.
Для отдельного RoPE естественны tokens/s или pairs/s. FPS имеет смысл после
замера генератора видео с явно указанными разрешением, длиной, шагами и режимом.

Для следующего этапа оптимизации полезен **отдельный**, более дорогой профиль:

| Диагностика | Зачем |
|---|---|
| DRAM read/write bytes и достигнутая пропускная способность | Проверить реальное сокращение обмена, а не выводить его из peak VRAM |
| FP64-инструкции и utilization, арифметическая интенсивность / roofline | Различить ограничение вычислениями FP64 и памятью |
| Регистры на поток и spill loads/stores | Обнаружить выгрузку промежуточных значений из регистров |
| Achieved occupancy, причины stalls | Объяснить недостаточное перекрытие задержек |
| Эффективность обращений, L1/L2 hit rates | Объяснить поведение памяти на разных размерах |

Эти аппаратные счётчики пока не измерены. Полезные input+output GB/s в отчёте
не являются измеренным DRAM bandwidth. Occupancy и TFLOPS не максимизируются
сами по себе: успешный критерий замены есть меньшее время при нужной точности.
Сбор Nsight изменяет условия выполнения, поэтому его результаты не подмешиваются
к обычным измерениям latency. Описание диагностик:
[Nsight Compute Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html).

Статьи для этого сопоставления:
[RoFormer](https://arxiv.org/pdf/2104.09864),
[FlashAttention](https://arxiv.org/pdf/2205.14135),
[Triton, MAPL 2019](https://www.eecs.harvard.edu/~htk/publication/2019-mapl-tillet-kung-cox.pdf).

## Численная политика компиляции

У обычного Inductor по умолчанию может исчезать промежуточное округление при
объединении соседних FP16/BF16-операций. Рукописное ядро создаёт другую границу
fusion, поэтому весь compiled-блок может отличаться даже при одинаковом RoPE
на одинаковых входах. Диагностика сохранена отдельно как `block_diagnostics.json`.

В основном конфиге у **обоих** вариантов обычный `torch.compile`,
`compile_options: {}`. Опция `emulate_precision_casts=True` изучена отдельно:
она влияет на округления, но не является гарантией побитного равенства любого
блока на любых размерах. Ради прохождения теста настройки рабочей модели не менялись.

Тест ядра требует побитного равенства вещественному FP64-эталону после заданного
округления. Eager-версии целого BF16-блока также должны совпадать побитно.
Для compiled-блока независимо оцениваются обе реализации относительно одинакового
FP32-блока с теми же весами, повышенными до FP32, и math SDPA. Порог интеграции:
новая относительная L2-ошибка не более чем на 5% выше исходной, плюс FP32-floor
1e-7. Максимальная абсолютная ошибка проверяется отдельно: не выше исходной
плюс один шаг низкой точности на масштабе максимума эталона. Это явно выбранные
инженерные допуски, не норматив из статьи. Все исходные ошибки сохраняются,
побитное равенство compiled-блока не заявляется.

Комплексный FP64-эталон дополнительно проверяется отдельно: порядок операций
комплексного CUDA-умножения может давать другое округление. Для FP16/BF16/FP32
задан допуск масштаба одного шага представления, для FP64 допуск уровня roundoff.

## Производительность

Варианты измеряются на одинаковых тензорах после общего прогрева. В каждом из
30 раундов порядок перемешивается с фиксированным seed. После обычного прогрева
каждому варианту даётся ещё 200 мс GPU-работы для стабилизации частоты. Время
снимается CUDA events вокруг CUDA graph replay и делится на число вызовов:
100 для малых входов, три для остальных.
Следовательно, квантили описывают среднее время группы вызовов, не хвост
распределения отдельных запусков и не end-to-end задержку приложения.

Проверяются малые сетки, рабочий чанк, большой вход FP16/BF16/FP32 и batch 2
на той же большой сетке. Корректность дополнительно проверяется для batch 1/2/4/8
на одинаковой сетке. Отдельно измеряется настоящий локальный WanBlock со случайными
одинаковыми весами и PyTorch Flash SDPA. Это не замер inference с checkpoint.

Допускается до 5% изменения времени как локальный порог шума. Проверяются и
медиана парных отношений, и отношение медиан, чтобы один способ агрегации не
скрыл регрессию другого. В таблице ускорение равно отношению показанных p50.
Все регрессии больше порога дают ненулевой код возврата. Bootstrap
является диагностикой вариации внутри одного прогона. Тридцать раундов и p99
не доказывают универсальную статистическую значимость на других устройствах.

## Источники

- [RoFormer, раздел 3.2](https://arxiv.org/abs/2104.09864): вращения, сохранение нормы,
  зависимость скалярного произведения от относительной позиции. Тестируются свойства,
  а не приписывается статье конкретный экспериментальный порог.
- [Исходный Wan2.1 RoPE](https://github.com/Wan-Video/Wan2.1/blob/9737cba9c1c3c4d04b33fcad41c111989865d315/wan/modules/model.py):
  индексация временной и двух пространственных осей и контракт upstream.
- [Официальный Triton vector-add tutorial](https://triton-lang.org/main/getting-started/tutorials/01-vector-add.html):
  проверка относительно эталона, прогрев и измерение полезной пропускной способности.
- [Triton в torch.compile](https://docs.pytorch.org/tutorials/recipes/torch_compile_user_defined_triton_kernel_tutorial.html):
  регистрация оператора, поддержка autograd и компиляции.
- [PyTorch opcheck и gradcheck](https://docs.pytorch.org/docs/stable/library.html#testing-custom-ops):
  корректность регистрации и математическая корректность производной различаются.
- [Численная политика Inductor 2.8](https://github.com/pytorch/pytorch/blob/v2.8.0/torch/_inductor/config.py):
  комментарий и параметр `emulate_precision_casts`.
