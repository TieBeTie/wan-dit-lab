# Harness

`configs/harness.json` задаёт общие измерения и проверки. Эксперимент меняет
только нужные поля в секции `harness`. Итоговый конфиг сохраняется с результатом.
Неизвестные параметры и неверные типы в `harness`, `pipeline`, `run` и `debug`
останавливают запуск до загрузки модели.

```text
src/wan_dit_lab/
  models/        Wan, attention, нормы, исходный RoPE, T5, VAE
  generation/    поток видео и sampler
  kernels/       Triton RoPE, FP8-запись, Sage KV
  quantization/  FP8, W4A4 и файлы весов
  offloading/    ресурсы, размещение, переносы, модель стоимости
  runtime/       pipeline, компиляция, окружение CUDA
  harness/       измерения, конфиг, метрики, проверки
  experiments/   сценарии RoPE и телеметрия Live
  reports/       представление сохранённых результатов
```

В `harness/timing.py` остаются циклы CUDA events, wall time и парного сравнения.
`runner.py` выбирает пробы по конфигу. `workload.py` содержит WorkloadRun.
`streaming.py` считает сводку уже выполненного потока, не запускает его повторно.
Старые публичные функции доступны через `from wan_dit_lab import harness`.

## Запуск

```powershell
$env:PYTHONPATH = 'src'
.\.venv\Scripts\python.exe -m wan_dit_lab.cli run --config configs/experiments/live.json
.\.venv\Scripts\python.exe -m wan_dit_lab.cli run --config configs/experiments/cache_fp8_live.json
```

Первый конфиг выбирает `run.mode: live`, второй `benchmark`. Наличие секции
`harness` не выбирает режим. Общая нагрузка лежит в `configs/base/live_512x928.json`.

`pipeline` задаёт порядок замен `rope`, `kv_store`, затем `compile`.
Параметры лежат внутри соответствующего шага. `debug` включает графы и сообщения
о перекомпиляциях средствами PyTorch. Это адаптеры существующей модели,
не отдельный компилятор и не FX-проходы.

Перед запуском выполняется `harness.checks.tests`. Пустой список отключает
эту проверку с явным статусом `disabled`. Ошибка теста останавливает запуск.
Прогрев и калибровка происходят до измеряемых чанков. Текущий Live использует
два слота offloading, калибровка измеряет их готовность и не подменяет их FlexGen.

## Настройки и память

`warmup`, `number`, `repeat`, `seed` задают операторный замер. `warmup_chunks`
и `measured_chunks` задают поток. `timing` выбирает CUDA graph либо CUDA events
и время стабилизации. `metrics` включает отдельные группы проб. Отключённые
пробы памяти, профилировщика и wall time в операторном runner и Live не выполняются.
Старый ресурсный runner сохраняет снимки, которые нужны самому алгоритму offloading,
независимо от выбора отображаемых метрик.

| Показатель | VRAM | RAM |
|---|---|---|
| Исходная | allocated после прогрева | RSS после прогрева |
| Текущая | allocated в конце участка | RSS в конце участка |
| Пиковая | max allocated аллокатора | максимум выборок RSS |
| Свободная | минимум глобальной free | минимум системной available |
| Reserved | отдельно: max reserved аллокатора | общего аналога нет |

RAM и свободная память опрашиваются с `memory.sample_interval_s`. Краткие пики
между выборками могут быть пропущены. Бюджет памяти является настройкой,
а не измеренной занятой памятью. `memory.vram_fraction: null` не вводит лимит.
Отсутствующее измерение сохраняется как null, а не ноль.

Число ядер берётся из GPU-событий CUPTI. Если после повторной пробы они
отсутствуют, считаются kernel-узлы захваченного CUDA Graph, включая вложенные
графы. Поле `source` различает эти способы. Второй способ не восстанавливает
GPU-времена отдельных ядер. Если оба способа недоступны, проверка завершается ошибкой.

Новая схема метрик не восстанавливает RAM прошлых запусков, где она не измерялась.
Исторические результаты не перезаписываются при переносе исходников.
