# Полный эксперимент offloading: подготовка

Статус: большая серия остановлена пользователем. Ниже сохранён план будущего сравнения. Готовы 5 baseline-роликов 2×2; прежние профили меняли только окна весов. Новый механизм переносов описан в разделе «Реализованные переносы». Калибровку и большую серию автоматически не возобновляем.

## Три способа: 2×2, FlexGen: медиана, FlexGen + запас

Один общий граф времени жизни. Три измеряемых способа: исходное 2×2 для весов, модель по медианам, та же модель с запасом. Два профиля модели используют один общий набор калибровочных замеров. Название FlexGen в таблицах означает собственную реализацию по идее статьи.

| | 2×2 | FlexGen: медиана | FlexGen + запас |
| --- | --- | --- | --- |
| Подготовка / перенос | Фиксированное окно 2×2 | Медианы длительностей | Наблюдённые максимумы |
| Время до использования ресурса | Без модели времени | Из расчёта по медианам | Раннее использование, из наблюдённых минимумов вычислений |
| Приоритет | Подгрузка следующего блока | Предсказанное полное время | Сначала отсутствие расчётных опозданий, затем время |
| Область | Перенос весов при общем графе времени жизни | Все управляемые ресурсы полного конвейера | Те же ресурсы и узлы |

Медиана является нашим вариантом модели по идее [FlexGen, §4.3](https://arxiv.org/html/2303.06865), а не требованием статьи. В статье модель параметризуется профилированием оборудования; максимумы перекрывающихся стадий не означают p100 длительностей.

Конфигурация: `configs/experiments/offloading_full_30s.json`. 24 разных проверочных промпта, по одному seed, три новых процесса на промпт. Шесть перестановок порядка режимов встречаются по четыре раза. Промпты выбраны детерминированно до запуска и не пересекаются с восемью промптами калибровки. Промпт, seed, точность, формы и бюджеты совпадают. Полный граф остаётся в обоих. Бюджет ограничивает одновременно резидентные ресурсы. NVIDIA GeForce RTX 4060 Laptop GPU имеет 8188 MiB VRAM; оба численных рабочих бюджета надо зафиксировать до калибровки с учётом runtime и прочих потребителей.

123 латентных кадра, 41 чанк дают 489 декодированных кадров. Для ровно 30 секунд при 16 кадрах/с сохраняем первые 480. Время и память учитывают все 41 чанк и закрытие MP4. Число сгенерированных и сохранённых кадров записывается раздельно.

## Калибровка и планирование

1. Собрать один набор повторных замеров на восьми разных промптах из конфига при 480×832. Промпт основного сравнения в этот набор не входит. Отдельные группы замеров: ресурс/операция, форма, dtype, пустой/заполняемый/полный KV, первый/прогретый decoder, режим перекрытия переносов и вычислений. Число повторов зафиксировать до сбора. Сохранять все наблюдения, количество, минимум, медиану, p90, p99 и максимум.
2. Построить общий явный порядок узлов и uses, first/last ресурсов. Учесть повторные использования KV и состояния decoder. Зафиксировать безопасное переиспользование storage. Ресурсами нельзя произвольно двигать: код, библиотеки и CUDA-контекст имеют ограничения runtime.
3. По медианам построить варианты расписаний и рассчитать очереди подготовки, переноса и вычисления. Выбрать минимальное предсказанное полное время при соблюдении обоих бюджетов памяти.
4. Из тех же замеров построить профиль с запасом: медленная подготовка/перенос и быстрое приближение момента использования. Память ограничивать максимальными размерами. Раннюю подгрузку разрешать при свободном бюджете. Проверять планы также по целым сохранённым калибровочным трассам. Кандидат с недостаточным временем подгрузки или памятью помечать непригодным для цели нулевых расчётных опозданий; не скрывать это задержкой самого потребителя.
5. Зафиксировать оба плана до основного сравнения. Во время выполнения реальные CUDA-события всё равно защищают готовность ресурсов и освобождение после последнего пользователя.

Наблюдённый максимум не является доказанной верхней границей будущих задержек. Минимум вычисления тоже не является доказанной нижней границей. Нельзя обещать 100% своевременной готовности по конечной выборке. Цель второго профиля: ноль наблюдённых опозданий, с обязательным измерением числа и длительности ожиданий. Чтение неготовых данных запрещено в обоих профилях.

Это собственный ограниченный поиск расписаний, а не интеграция полного оптимизатора FlexGen и не гарантия глобального оптимума.

## Измерения

Одна сравнительная таблица находится в `notes/research/Offloading.md`, машиночитаемый шаблон `comparison.csv` в папке эксперимента. Пустая ячейка / точка означает отсутствие замера, не ноль.

| Метрика | Определение |
| --- | --- |
| Полная генерация | Вход в процесс → закрытие MP4, включая загрузку моделей, T5, все чанки и декодирование |
| Опоздания и ожидания | Момент готовности относительно момента необходимости; число опозданий, суммарное и максимальное GPU-ожидание ресурсов. Не путать с CPU, опередившим очередь GPU |
| Первый кадр | Вход в процесс → передача первого декодированного кадра writer |
| Чанк | Интервал между доставкой последовательных чанков; включает denoise, decode и writer; первый чанк отдельно |
| p50 / p90 / p99 чанка | Чанки с индексом ≥ 7 при контексте 21 латентный кадр; линейная интерполяция квантилей |
| Выдача кадров | Число декодированных кадров измеряемых чанков / сумма интервалов этих чанков |
| VRAM тензоров | `torch.cuda.memory_allocated`; резерв allocator сюда не входит |
| Пик VRAM тензоров | Максимум allocator за весь процесс, без сброса на границах фаз |
| Резерв VRAM | `memory_reserved`, записан отдельно от живых тензоров |
| VRAM устройства | Total/free через NVML, used = total − free; включает runtime и другие процессы |
| RAM процесса | RSS и Windows private commit, раздельно; mmap входит в RSS |
| RAM системы | Доступная память всей системы, не память конкретного процесса |
| Pinned RAM | Активная и резервированная закреплённая память раздельно, если runtime предоставляет счётчики |
| Память после очистки | Снимок после освобождения ресурсов, до выхода процесса; процесс продолжает жить для замера |

Сэмплирование памяти каждые 100 мс, одинаковая инструментализация для обоих профилей. p50/p90/p99 памяти по всем временным сэмплам запуска; пики sampled RSS/device-used и минимум свободной памяти помечаются как выборочные, они могут пропускать короткие всплески. Пики CUDA allocator снимаются его собственным счётчиком. Без синхронизации каждого блока ради метрик. Перед запуском сохранить исходную свободную память, состояние GPU и версии.

По одному запуску каждого способа на каждом из 24 промптов; квантили считаем внутри запуска. Три исходные записи сохраняются отдельно. Калибровку показывать отдельно, не прятать в измеряемую генерацию. Использовать одинаково подготовленный compile-cache; его состояние фиксировать. Единица статистики — один промпт/seed. Первичные два сравнения с 2×2: точный двусторонний sign test относительно ускорения 1.05×, Holm при α=0.05. Все 24 тройки обязательны. При вероятности выигрыша 0.8 и отсутствии ties консервативная мощность 0.811; значимый результат не гарантирован. Guarded vs median и все покадровые метрики описательные. Не объединять чанки как независимые наблюдения.

## Учёт ресурсов

`resources.csv` содержит строки категорий, а полный реестр должен содержать записи из поля `inventory` протокола. Логический ID не меняется при копировании. Физические копии имеют отдельные storage ID. Разделяемые представления одного storage не прибавляют его объём повторно. Размеры динамических KV, активаций и decoder state записываются во времени. Неизвестные workspace библиотек остаются неизвестными, а не нулевыми.

Число ресурсов: уникальные логические ID за запуск. Память категории: максимум суммы уникальных физических storage этой категории, отдельно для RAM и VRAM. Пики категорий могут происходить в разное время, их нельзя складывать. Сумма управляемых ресурсов может быть меньше памяти устройства из-за неучтённого runtime; разницу сохранять как overhead.

События трассы: acquire → prepare → transfer → ready → execute → release, с ID ресурса, узла, размещением, размером и временем. Они нужны для проверки соблюдения плана и преждевременного освобождения.

## Готовность перед запуском

- Подключить один полный ресурсный план к обоим профилям.
- Подключить к нему оба профиля scheduler и зафиксировать кандидатные политики.
- Подключить счётчики, inventory, трассу и writer с обрезкой до 480 кадров.
- Зафиксировать оба численных бюджета, план калибровки и два производных профиля.
- Проверить короткий проход: порядок ресурсов, cleanup, число кадров, совпадение всех латентных чанков и декодированных кадров до MP4-кодирования. Критерий по умолчанию побитный; возможные допуски определять до основных замеров.
- Только затем выполнить 72 полных запуска по 30 секунд, три способа на каждом из 24 промптов. Ошибка/OOM не заменяются числом в таблице.

Фактические политики сохраняются в policies.json. Протокол, исходники и метаданные checkpoint фиксируются; изменение исходников останавливает дальнейшие запуски. Готовые случаи можно продолжить только при том же протоколе и коде.

## Реализованные переносы

`resource_store.py`: TensorStore хранит тензорные ресурсы в RAM или отдельных файлах; StateBinding восстанавливает их к использованию и выгружает после него. Новая копия завершается до удаления актуальной. При ошибке записи живой владелец сохраняется. Файлы заменяются атомарно; квоты проверяются до освобождения данных. Повторно записывать неизменённые веса не требуется.

| Ресурс | Граница использования | Вне VRAM |
| --- | --- | --- |
| Веса T5 / DiT | Блок, прежний BlockOffloader | Checkpoint через mmap, окно pinned RAM |
| Self-attention KV, кольцо, PC / decay metadata | attend, commit, reset, forget | RAM или файл; скалярные счётчики остаются у KVCache |
| Cross-attention KV | Блок; обновление при смене промпта | RAM или файл; интерполяция остаётся на исходном устройстве |
| Веса TAEHV | decode | RAM или файл; модуль между использованиями на meta |
| Состояние TAEHV | decode, включая перенос между чанками | RAM или файл; trim не сбрасывается |
| Латенты для recache | Ограниченное окно истории | RAM или файл, старые элементы удаляются |
| Архив латентов | Сохранение чанка | RAM или файлы чанков + latents.json; дисковый архив собирается без полной загрузки в RAM |
| Активации / workspace | Текущая операция | Сразу используемые данные остаются в VRAM; после последнего использования освобождаются |
| Код / CUDA-контекст | Runtime | Управляются библиотеками и драйвером |

Подключено в `scripts/experiments/offloading_generate.py`. Явная политика: `configs/experiments/offloading_resource_migration_policy.json`. Она сохраняет окно весов 2×2 и задаёт размещения остальных поддерживаемых ресурсов. Без поля resources сохраняется прежнее размещение. CUDA graph capture с переносимыми ресурсами отклоняется: адреса меняются.

Один pinned-буфер ограниченного размера переиспользуется после завершения копии. Переносы синхронны на границе ресурса; это реализация для проверки корректности. Перекрытие переносов KV / VAE с вычислениями и автоматический подбор их размещений по модели стоимости пока не подключены. Старый `offload_policy.py` продолжает выбирать только окна весов; не считаем его полным FlexGen.

Квоты TensorStore ограничивают сохранённые копии и место для атомарной замены. Временные CPU-тензоры одного восстанавливаемого / сериализуемого ресурса, pinned staging, checkpoint pages и runtime требуют отдельного запаса. Это не ограничитель полного RSS. Разные представления общего storage внутри одного ресурса отклоняются без адаптера владения; одна и та же ссылка на тензор поддерживается. Ресурсы должны иметь явного владельца. Переносы выполняются в текущем CUDA stream, зависимости от внешних producer streams задаёт вызывающий код.

События save / restore и пики сохранённых RAM / disk копий записываются в record.json. Они отдельны от прежней трассы переносов весов и от счётчиков памяти процесса / устройства.

Проверка: `.venv/Scripts/python.exe -m pytest tests/test_resource_store.py tests/test_resource_schedule.py tests/test_offload_runtime.py tests/test_kv_cache.py tests/test_resource_lifetime.py tests/test_offload_policy.py tests/test_prefetch_model.py tests/test_causal_schedule.py -q`.

Проверяем точное сохранение dtype / значений, PC / кольцо / decay, смену промпта и recache, RAM / disk, ограниченный pinned-буфер, ошибки записи / квот, очистку при сбое. CUDA-тесты используют небольшой DiT и настоящий TAEHV; интеграционный тест проходит до MP4 и сравнивает хеши латентов и кадров до кодирования. Итог локальной проверки: 73 теста прошли, Ruff без ошибок. Dynamo проверен с backend=eager. Полный Inductor, реальная модель при 480×832 и скорость новых размещений ещё не проверены; большую серию не запускали.
Калибровка каждого промпта: 30 латентных кадров, 10 чанков; для steady compute fit используются чанки 8 и 9, после заполнения контекста и первой компиляции полной формы. Все сырые времена сохраняются. Загрузка оценивается по реальным trace pack/copy. В guarded-профиле выбирается минимальное предсказанное превышение времени относительно цепочки с готовыми ресурсами. Если нулевое превышение недостижимо, поле predicted_zero_excess остаётся false; гарантия не заявляется.

Перед проверочной серией два рассчитанных плана проходят полный 10-чанковый gate с eviction KV: побитное сравнение всех латентов и декодированных кадров с калибровочным 2×2. Непрошедший gate останавливает всю серию.

Учёт tensor storage выполняется в выбранных снимках, это аудит наблюдаемых storage, а не точный peak внутренних временных workspace. Число ресурсов в сводке относится к явно управляемым владельцам. Размер mmap storage в RAM является логическим объёмом отображения и может превышать его физически резидентные страницы. Общие пики памяти измеряются независимо и включают неатрибутированный overhead.
