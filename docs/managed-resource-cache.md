# Управляемый кэш ресурсов

Одна политика размещения для сохраняемых тензоров:

$$
\mathrm{VRAM}\rightleftarrows\mathrm{RAM}_{\mathrm{cache}}
\rightleftarrows\mathrm{SSD}.
$$

| Ресурс | Обращение к файлу |
|---|---|
| Неизменяемые веса checkpoint | Read; исходный mmap, без повторной записи |
| Изменённый self-attention KV и состояние decoder | Write при вытеснении, Read при возврате |
| Неизменённое состояние с актуальной файловой копией | Read при возврате; без повторного Write |
| Cross-attention KV, история латентов | Та же политика; новая версия заменяет прежнюю |

Активный ресурс защищён от вытеснения. Неактивные ресурсы удерживаются в пределах общих бюджетов VRAM и RAM. При недостатке RAM актуальная версия явно сохраняется в файл до освобождения тензора. Предзагрузка допускается только при наличии места.

Без профиля стоимости для известной последовательности сначала вытесняется ресурс с наиболее далёким следующим использованием; для неизвестного порядка используется давность обращения.

Для рабочего профиля веса блоков DiT один раз преобразуются в BF16 на диске (`python -m wan_dit_lab.quantization.weight_pack --output artifacts/self_forcing_dit_blocks.bf16`). Во время генерации читается неизменяемый mmap готовых блоков, без повторного преобразования FP32 → BF16 и без полной частной BF16-копии в RAM. Буферы загрузки весов учитываются отдельно от сохраняемых данных.

Рабочие тензоры операции и память CUDA/runtime не сериализуются произвольно. Для них предусмотрен запас; ограничения кэша не являются строгим ограничением полного RSS процесса. Резидентностью файлового кэша ОС менеджер не управляет.

Конфигурация: `configs/experiments/offloading_managed_resources_policy.json`. Исторические 15 роликов относятся к сравнению окон весов. Compiled-проверка общего кэша: `outputs/experiments/2026-10-19/20_Offloading_compiled_30s`. Диагностика готовности ресурсов: `outputs/experiments/2026-10-19/21_Device_prefetch_5s`.

## Модель стоимости

Профили `offloading_managed_cost_median.json` и `offloading_managed_cost_guarded.json` включают измеренную модель для общего кэша. Целочисленная оптимизация выбирает ресурсы для вытеснения, минимизируя стоимость потери повторного использования при требуемом освобождении памяти. Стоимость учитывает восстановление, запись изменённой версии и расстояние до следующего использования. Предзагрузка до VRAM назначается по оценке времени загрузки и времени вычислений до потребителя.

Медианы используют медианы измерений. Запас использует максимум загрузки/записи и минимум вычислений. Проверенный профиль с запасом: `offloading_managed_cost_guarded.json`, калибровка `22_Calibrated_prefetch_5s/calibration_uniform_live.json`. Медианный вариант читает ту же калибровку; его производительность в этой ревизии отдельно не измерялась. Отсутствующий замер является ошибкой. Сами профили не запускают генерацию.

В каждом управляемом прогоне сохраняется `resource_calibration.json`. Его стоимости включают файловый кэш ОС, не являются холодной скоростью SSD. Для сравнения нужны одинаковые разрешение, нагрузка и условия кэша; старые замеры только окон весов не дают калибровку KV Read/Write.

Это адаптация идеи FlexGen, не его исходная LP-модель: ресурсы неделимы, используется MILP и стоимость повторного использования. Окна весов остаются отдельным механизмом.

## Готовность к потребителю

`prefetch_device` переносит сохранённую версию из RAM или mmap в VRAM на отдельном CUDA-потоке. Future завершается после копирования. Для него заранее резервируются VRAM и отдельный ограниченный pinned-буфер. Спекулятивная загрузка не вытесняет другие GPU-ресурсы. Перезапись, удаление и закрытие ждут незавершённый перенос, поэтому старая версия не может заменить новую.

Старая проба удерживать KV на весь блок (`21_Device_prefetch_5s/fused`) отключена. В проверенном профиле `commit_in_attention=true`: финальный `commit` выполняется внутри уже открытой аренды attention, до её освобождения. FFN не продлевает аренду. Проверки со сменой промпта, PC и recache сохраняют результат.

Обновление GPU-ресурса удаляет устаревшую RAM/SSD-копию; актуальный владелец остаётся в GPU. Чистая копия для readonly-ресурса сохраняется. При заполнении RAM оптимизатор сравнивает вытеснение сохранённого ресурса с прямой записью входящего на SSD: обязательного приёма в RAM больше нет.

Полная калибровка проводится до освобождения stream: три readonly-пробы для каждого живого ресурса. Для 30 KV-блоков с одинаковым размером 203773440 байт используется общая измеренная огибающая времени переноса. Это 192 реальных восстановления и 90 чтений с диска, без умножения числа наблюдений на число блоков. Время очереди копирования учитывается до назначения предзагрузки. Лимит GPU-кэша 6336 MiB получен из инвентаризации постоянных ресурсов; общий предел CUDA остался 7.25 GiB.

Результаты и ограничения короткого теста: `outputs/experiments/2026-10-19/22_Calibrated_prefetch_5s/Comparison.md`. При меньшем GPU-кэше 5.5 GiB также измерены нулевые опоздания, но скорость ниже. Когда данные помещаются в VRAM, менеджер удерживает их там; поддержка SSD не означает обязательную выгрузку горячего KV.

В `record.json`:

| Метрика | Что измеряет |
|---|---|
| `consumer_ready.ready_at_request` | Готов ли ресурс в VRAM при обращении |
| `consumer_ready.consumer` | Операция, запросившая ресурс |
| `prefetch_wait.duration_s` | Ожидание Future в RAM или VRAM |
| `pack_wait_s` | Ожидание CPU-очереди подготовки весов |
| `dependency_wait_s` | CUDA-зависимость перед вычислением блока |
| `compute_stream_gap_s` | Промежуток между блоками на вычислительном CUDA-потоке |

Host-ожидания могут перекрываться с работой GPU. Их сумма не равна простою GPU. Если предзагрузка не успела, потребитель ждёт и это обращение учитывается как опоздание. Эмпирический максимум калибровки не гарантирует нулевое ожидание.
