# Отчёт для продолжения: лосс при сжатии 704x1280 → 608x1120 · 2026-11-11

Самодостаточный документ для модели, которая продолжит исследование. Читать вместе с `docs/handoff-2026-11-11-loss-search.md` (план этапов) и концом `docs/STATE.md`. Всё ниже, кроме раздела 6, измерено. Где число взято из старых записей, указан источник.

## 1. Цель

Модель LongLive-2.0-5B (2 шага, W4A4 SVDQuant, Sage 2, KV FP8) обучена только на 704x1280 (сетка токенов 22x40). На 8 ГБ VRAM она даёт 5.4 fps. Нужно сжать кадр, чтобы ускориться, и при этом остаться как можно ближе к 704.

$$
\min_{\mathrm{cfg}}\ \mathcal L(\mathrm{cfg})=\mathrm{LPIPS}_{\rm align}+\bigl(1-\mathrm{DINO}_{\rm ref}\bigr)\quad\text{при}\quad \mathrm{FPS}\ge 15,\ \ M_{\rm VRAM}\le 8\ \text{ГБ},\ \ M_{\rm RAM}\le 16\ \text{ГБ}
$$

L считает `scripts/reports/evaluate_videos.py`: LPIPS после подбора масштаба и сдвига к эталону плюс 1 минус косинус DINOv2 между кадрами в один и тот же момент. Эталон: прогон 704 того же сида, тех же сцен, того же порядка цепочек и того же числа чанков.

| Что | Значение | Источник |
|---|---|---|
| Главный кандидат | 608x1120, PI M 1.1 (или NTK 1.2) | STATE, 2026-11-09 |
| FPS 608 | 7.96 последнего чанка, 4.02 с на чанк | прогон 2026-11-11, раздел 4 |
| FPS 576 | 9.2, лосс хуже | STATE |
| Требование | 15 fps, то есть ещё около 2x | |

## 6. Гипотеза: парный лосс к 704 местами неподходящий

### 6.1. Почему

Парный лосс сравнивает одно видео с одним другим видео. Он имеет смысл, только пока две траектории шума остаются одной траекторией. Измерения показывают, что это не так даже для одного и того же конфига.

| Где парный лосс ломается | Число | Что он меряет вместо качества |
|---|---|---|
| Любой чанк после первого | латент первого чанка двух одинаковых прогонов расходится на 36 до 42% нормы | расхождение траекторий, одинаковое для хорошего и плохого конфига |
| Сравнение между сценами | пол лисы 0.27, чашки 0.18 | подвижность сцены: движение быстрее разводит траектории |
| Один эталон | эталон сам одна случайная выборка из хаотического процесса | расстояние до случайной точки, а не до «правильного» видео |
| Локальные дефекты (вторая ручка чашки) | ручка видна глазами, лосс её почти не видит | для этого уже есть `--crop` (`lpips_aligned_crop`) |
| «Поведение не клеится» | шов (`seam`) у 704 повтор: лиса 1.69 до 1.78, у 608: 1.44 до 1.75 | парный лосс швов не видит вообще. По швам 608 не хуже самого 704 |
| Оптимизация (CMA-ES, этап 4 handoff) | шум 0.05 при каждом вызове | случайная функция, оптимизатор найдёт удачный шум |

### 6.2. Где парный лосс ещё годится

Первый чанк: до него траектории не успели разойтись так сильно. Лосс только первого чанка (`lpips_aligned_first + 1 - dino_reference_first`):

| | лиса | чашка |
|---|---|---|
| Пол 2 (две пары повторов 704) | 0.203 / 0.234 | 0.165 / 0.174 |
| 608 NTK 1.2, сиды 0/1/2 | 0.377 / 0.504 / 0.493 | 0.310 / 0.323 / 0.352 |
| 608 PI 1.1, сиды 0/1/2 | 0.406 / 0.495 / 0.378 | 0.250 / 0.230 / 0.266 |

Лосс первого чанка почти равен лоссу всего видео. Значит, почти всё, что 608 теряет, теряется сразу, и это можно мерить на одном чанке (около 5 с на точку через `generate.rope_sweep`). Пол первого чанка (0.17 до 0.23) пока тоже велик, потому что ветка W4A4 недетерминирована.

### 6.3. Какие лоссы взять вместо или вместе

| Лосс | Что меряет | Где применять | Цена |
|---|---|---|---|
| Парный, первый чанк, после детерминированной W4A4 | ошибку самого вычисления на 608 | поиск RoPE и расписания, CMA-ES | нужна правка `lora.cuh` |
| Парный, нормированный на пол и потолок: (L − L_пол) / (L_потолок − L_пол) | долю устранимого зазора, сравнимую между сценами | итоговые таблицы | бесплатно, пол и потолок уже есть |
| Распределительный (непарный): KID или FD по признакам DINOv2 / CLIP между множеством клипов 608 и множеством клипов 704 по многим сидам | похоже ли 608 на 704 как распределение, без требования той же траектории | выбор финального профиля | много сидов: около 8 x 2 сцены x 3 чанка на точку |
| По латентам первого чанка: 608 против уменьшенного по площади латента 704, по каналам (среднее, дисперсия, спектр) | сдвиг статистик до декодера | быстрый отбор, `descent.json` уже пишет среднее и дисперсию каналов | бесплатно |
| Временная согласованность своего видео: `seam`, DINO между соседними кадрами, мерцание | «клеится ли» видео само с собой | жалоба пользователя на склейку | бесплатно, метрики есть |
| CLIP к промпту | слушается ли промпта | страховка от «красивого, но не того» | бесплатно, `clip_text` есть |
| Локальный LPIPS (`--crop`) | известные дефекты: ручка, лишний предмет | контроль, не цель | бесплатно |

Предложение: целевая функция для поиска = парный лосс первого чанка (после детерминизации), отбор финала = распределительный лосс по многим сидам плюс швы и глаза пользователя.

## 9. Правила проекта

- Генерация только `bin\wan.exe --config <json>` (очередь встроена), снимок конфига рядом с выходом.
- Никаких зашитых констант, строгий контракт конфига.
- Любой код: сначала падающий тест.
- Архитектурные изменения (контракт окна, ядра в `ops/`) сначала объяснить пользователю и ждать «да».
- `src/wan_dit_lab/models/rope.py` не трогать.
- Во время прогона ничего не писать на SSD, KV на диск нельзя.
- Ничего не удалять, не коммитить, не пушить без просьбы.
- Сравнивать лоссы только при одном числе чанков и одном порядке цепочек.
- Решает пользователь глазами по сеткам, метрики его решение не заменяют.
