# Frequency-aware RoPE: настройка и границы реализации

Реализуется как постоянный пространственный профиль при подготовке RoPE-таблиц. Это не дополнительный слой, не отключение RoPE и не новый обучаемый модуль. Существующие attention-ядра получают те же таблицы cos/sin той же формы.

Основание: [Lumina-Next, §2.2, Frequency-Aware Scaled RoPE](https://arxiv.org/html/2406.18583#S2.SS2). Ниже используется наша явная нумерация реальных каналов Wan, чтобы опорная частота определялась физическим условием длины волны.

Для одной пространственной оси:

$$
\theta_j=10000^{-2j/D},\qquad
j_* = \frac{D}{2}\log_{10000}\frac{L}{2\pi},\qquad
\frac{2\pi}{\theta_{j_*}}=L.
$$

Здесь D=42, j=0,...,20, L — обученная длина оси **в токенах**, то есть 22 для H и 40 для W. Индекс j_* вещественный; округлять его не требуется.

Постоянный профиль:

$$
\theta'_j=\theta_j M^{\min(j/j_*,1)}.
$$

При M<1 это эквивалентно изменению основания с ограничением снизу результатом Position Interpolation. При M>1 используется обратное направление ограничения, сверху результатом PI. **Этот перенос на растяжение уменьшенной сетки — наша адаптация, а не проверенный в статье режим.** Нельзя буквально оставить исходный max при M>1: тогда изменение низких частот превысит выбранное M.

Если L≤2π, ни одна пара не делает полный оборот на обученной оси; профиль использует равномерное масштабирование. M=1 даёт исходные частоты. Временная таблица видео остаётся прежней.

У NTK опорная пара — самая низкая (j=20); здесь опора определяется длиной обученной оси, поэтому изменение насыщается раньше. Это не гарантирует преимущество над NTK и не гарантирует геометрический зум.

## Как включить

В объекте `export.rope` при `interpolate: true`:

```json
{
  "interpolate": true,
  "native_size": "704x1280",
  "scene_offset_frames": 8,
  "stretch": 0.2992905106483072,
  "by_parts": null,
  "ntk_aware": false,
  "frequency_aware": true
}
```

`stretch` — показатель t, а не множитель частот: M_H=(22/16)^t, M_W=(40/29)^t для 512×928. Пример выше задаёт M_H=1.1. Одновременно включать frequency-aware с NTK или by-parts нельзя. Старые конфиги не обязаны добавлять новое поле; при его отсутствии прежние профили сохраняются.

Выбор профиля происходит один раз в Python при создании таблиц для экспорта. В горячем пути attention не появляется дополнительного условия; RoPE продолжает применяться тем же ядром. Изменение профиля меняет идентичность экспорта и требует отдельных пакетов с правильными константами.

Time-aware и Context Drop этой реализацией не включаются. Frequency-aware постоянен по шагам денойзинга, поэтому сам по себе не вводит смену фазового соглашения между сохранёнными ключами видеокэша и текущими запросами.
